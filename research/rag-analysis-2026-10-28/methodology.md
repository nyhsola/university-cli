# Методика расчётов и воспроизводимость

Анализ выполнен 28 октября 2026 года. Входы: исходные report.json/compare.json нового запуска, report.json предыдущего запуска, связанные operation logs, SQLite в режиме read-only, текущие JSON-конфигурации/датасеты и `experiment-evidence.json`. Перечень SHA-256 и определения сохранены в `provenance.json`.

Код приложения, конфигурации, датасеты и сохранённая база не менялись. Аналитические вычисления и временный FTS replay не вызывали Ollama. Файлы нового исследования записаны только в эту папку. Сборка приложения для такого анализа не нужна.

**1. Единицы анализа и знаменатели.**

- 3120 запланированных оценок, 3119 сохранённых ответов с ask-логом, 3117 judge-вердиктов.
- 30 разных пар datasetId/questionId: по десять вопросов на три книги.
- 104 комбинации indexProfileId/queryProfileId, по 30 оценок в каждой.
- Complete rate по плану: complete / число запланированных оценок. Неоценённый случай даёт ноль complete, но отдельно сохраняется как error, а не incorrect.
- Scored complete rate: complete / число реально оценённых. Общие значения — 58,27% и 58,33% соответственно.
- Категории тэгов агрегируют повторные оценки тех же вопросов. Для multi-hop число 312 означает три вопроса × 104 конфигурации.

При агрегации по index-профилю каждой из 13 query-конфигураций дан одинаковый вес; по query-профилю — каждому из восьми index-профилей. Это свойства экспериментальной матрицы, а не оценка частоты реальных пользовательских запросов. В lexical-агрегации три embedding-профиля fixed1000 фактически являются повторениями одних prompts; для сравнения embeddings эти query-профили исключены.

Все исходные числа C/N/I и retrieval-метрики сверены с compare.json. Mean judge score является фиксированной кодировкой 10/5/0 и не считается независимой оценкой точности.

**2. Время и токены.**

Основное время запроса берётся из ask operation log. ReportQuestionResult.durationMs включает также judge и потому не подходит для сравнения пользовательской задержки без уточнения.

Суммарное время запуска — 76009,414 с. Index-операции — 9372,891 с; успешные ask-логи — 52021,123 с; judge — 14428,896 с; одна неуспешная генерация — 151,534 с. Остаток около 35 с включает запись/подготовку и прочую сопутствующую работу. Между суммой длительностей question rows и отдельными стадиями есть небольшая накладная работа.

Среднее ask вычисляется по доступным успешным ask-логам. В двух случаях judge error ask существует и включён. В случае generation error ask отсутствует, поэтому его 151,534 с не смешиваются с успешной latency-выборкой. Медиана и p95 вычисляются по тем же логам; p95 — линейный sample quantile NumPy.

Сообщённые токены на запрос: inputTokens + outputTokens. Input смешивает query embeddings, rewrite prompts и answer prompts; output включает rewrite и answer outputs. Это учёт нескольких разных операций, не унифицированная цена. По всем доступным записям:

| Стадия | Сообщённые токены |
|---|---:|
| Новая индексация | 5627394 |
| Запросы | 5277201 |
| Judge | 3071555 |

Счётчики потерянных вызовов не восстанавливались: значения не являются точным полным расходом с ошибками. Judge показан отдельно и не включён в пользовательские query-профили. Кешированные baseline-индексы имеют SKIPPED и ноль новых index tokens; это не означает бесплатного построения такого индекса.

Число векторов и объём BLOB считались по соответствующим индексам. MiB в таблицах — сумма length(vector) / 1048576, без SQL-индексов, текста, весов моделей и KV cache. Это не общий размер базы и не RAM/VRAM.

**3. Парные факторные сравнения.**

Проверены 16 контрастов по факторам, сформулированным в предыдущем плане. Они не были формально пререгистрированы; анализ остаётся исследовательским.

Query-контрасты: Q2→Q5, Q2→Q6, Q3→Q7, Q3→Q8, Q1→Q9, Q1→Q10, Q1→Q11, Q1→Q4, Q4→Q12, Q12→Q13. В каждом по 240 пар, но только 30 единиц ресэмплинга. Index-контрасты: I1→I3, I1→I4, I2→I5, I1→I6 — по 390 пар; I1→I7 и I1→I8 — по 300 пар, исключив lexical Q3/Q7/Q8.

Для каждого вопроса вычисляется средняя разница бинарного complete по остальным вариантам фактора. Таким образом, один вопрос даёт одно число, а не 8 или 13 независимых наблюдений.

Bootstrap: 10000 повторов, по десять вопросов с возвращением внутри каждой из трёх книг; среднее по 30 выбранным вопросам, percentile interval 2,5–97,5%. Он условен на фиксированные три книги и не оценивает дисперсию переноса на новые документы.

Permutation test: 20000 независимых sign flips тридцати вопросных разниц, двухсторонняя статистика абсолютного среднего, Monte Carlo p с поправкой +1. Seed 20261028. Используется предположение обменности направлений парной разницы под нулевой гипотезой; общие ошибки по книге и автоматическая разметка ограничивают интерпретацию.

Holm применяется к 16 p-values как к одной семье. После поправки порог 0,05 проходит только Q2→Q6. Это не превращает post-selection лидера из 104 конфигураций в подтверждённого победителя.

В отдельных диагностических сравнениях двух конкретных комбинаций используется exact McNemar по 30 вопросам. Такие p-values являются дополнительными, нескорректированными; их нельзя использовать для произвольного выбора самой выгодной пары после просмотра всей таблицы. Принцип выбора теста по устройству NLP-эксперимента обсуждается в [Dror et al., ACL 2018](https://aclanthology.org/P18-1128/).

**4. Независимая от chunkId проекция evidence.**

Вспомогательная source-разметка взята из предыдущего `experiment-evidence.json`, созданного до нового запуска. В ней есть точные цитаты и UTF-16 offsets в исходных UTF-8/CRLF книгах. Книги не содержат дополнительных Unicode code points за пределами BMP, что проверялось при подготовке; Python character offsets совпадают с используемыми здесь единицами Kotlin String.

Для всех layout без overlap исходный текст равен конкатенации последовательных чанков, поэтому ranges получены накоплением их длины. Для I2 base-разбиение совпадает с I5; start определяется как конец base-чанка минус длина overlap-чанка, затем вся подстрока проверяется по source. Все выбранные тексты из логов совпали с базой.

Для каждого выбранного source span вычисляется длина объединения его пересечений с отобранными ranges, делённая на длину span. Overlap не считается дважды. Альтернативные достаточные span используют max coverage; обязательные группы должны быть покрыты все. Для диагностической средней усредняются покрытия групп, для full_reference_evidence требуется ровно полное покрытие каждой группы.

Группировка явно сохранена в `evidence-grouping.json`. Например, два упоминания должности Starbuck — альтернативы, два факта Ishmael-survival — обязательные группы, у Argos используется span смерти, а вводное описание реакции является необязательным. По умолчанию отдельные curated spans считаются обязательными группами.

Саму группировку задавал аналитик после получения результатов; она не является независимой человеческой разметкой теста. Source quotes местами длиннее минимального достаточного доказательства, а альтернативные упоминания не исчерпаны. Поэтому full_reference_evidence нельзя переименовывать в истинный semantic fact recall. Его польза — одинаковая проверяемая система координат для разных размеров чанков, дополняющая исходный Recall@5.

Проекция рассчитана для 2807 отвечаемых успешных ask. Три unanswerable-вопроса во всех конфигурациях исключены; один generation failure тоже исключён. Разметка используется только офлайн, не передавалась retrieval или генератору. Полученная ассоциация с complete описательная, не причинная.

**5. Replay FTS и отрицательные контроли.**

FTS replay использует SQLite in-memory и те же исходные rowId/content. Старый corpus содержит только indexConfigurationId из прошлого отчёта; текущий — все сохранённые чанки. Tokenizer unicode61, query — уникальные исходные слова через OR, ограничение конкретной конфигурации и сортировка rank. Для всех 60 проверяемых lexical-случаев восстановлены соответствующие отобранные последовательности обоих прогонов.

Отрицательные контроли сравнивают I1/I7/I8 для Q3/Q7/Q8. Полное совпадение prompt проверяется через chunkId, текст, порядок и dense/lexical rank: renderer использует эти поля и fileName, но не indexId. В сравниваемых случаях fileName и вопрос также одинаковы.

Противоречия judge найдены группировкой точных actualAnswer внутри одного вопроса. Строки не нормализуются по регистру, пробелам или пунктуации; следовательно, число найденных противоречий консервативно относительно такого расширенного поиска.

**6. Что считать устойчивым выводом.**

Сильнее всего подтверждены фактические свойства артефактов: совпадение входов и контекстов, FTS-interference, одинаковые ответы с разными вердиктами, стоимость уже выполненных операций. Следующий уровень — условные различия качества по факторам на этих вопросах. Самый слабый — обобщение выбранного победителя на другие документы или объявление нового алгоритма эффективным без отдельной проверки.

Весь experiment является развитием на известных тридцати вопросах. Для проверки обобщения нужен новый test и контролируемая политика оценки.
