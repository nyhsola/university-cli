# Следующий эксперимент: профили и запуск

Матрица подготовлена по `analysis.md`: восемь index-профилей, тринадцать query-профилей и тридцать исходных вопросов в трёх датасетах. Полный запуск выполняет **3120 оценок**: 104 комбинации по 30 вопросов. Прежние 240 оценок входят в эту матрицу.

Все прежние профили сохранены без изменения файлов, IDs и параметров. Вопросы, expectedAnswer, теги и gold-разметка index-профилей 1/2 также сохранены. Новые профили проверяют поддерживаемые приложением варианты; поиск соседей, декомпозиция, reranking и настоящий токенный лимит в этот эксперимент не добавлены.

**Index-профили.**

| ID | Название | Разбиение | Embedding | Назначение |
|---|---|---|---|---|
| 1 | Default indexing | Fixed 1000 | Qwen3 8B | Прежний baseline |
| 2 | Recursive indexing | Target 900, max 1000, overlap 100 | Qwen3 8B | Прежний recursive baseline |
| 3 | Fixed 500 characters | Fixed 500 | Qwen3 8B | Более точные короткие фрагменты |
| 4 | Fixed 2000 characters | Fixed 2000 | Qwen3 8B | Более широкий локальный контекст, меньше векторов |
| 5 | Recursive 900 without overlap | Target 900, max 1000, overlap 0 | Qwen3 8B | Контроль эффекта overlap относительно ID 2 |
| 6 | Recursive 1000 without overlap | Target/max 1000, overlap 0 | Qwen3 8B | Контроль естественных границ относительно ID 1 |
| 7 | Fixed 1000 with 0.6B embeddings | Fixed 1000 | Qwen3 0.6B | Влияние размера embedding-модели относительно ID 1 |
| 8 | Fixed 1000 with 4B embeddings | Fixed 1000 | Qwen3 4B | Промежуточный размер embedding-модели |

Все размеры здесь измеряются в единицах Kotlin String/UTF-16, а не в токенах. Текущие книги не содержат символов за пределами BMP, поэтому одна такая единица совпадает с одним Unicode code point. Естественные границы recursive приводят к фактическим чанкам короче заданного target; одинаковый target не означает одинаковое распределение длин.

У новых budget-профилей 5–8 maxChunks=32 и candidateLimit=32: это позволяет заполнить расширенный бюджет даже при коротких чанках. У остальных maxChunks=10. Для чистого dense/lexical увеличение глубины списка сохраняет порядок начала выдачи; в расширенном контексте может быть использовано больше кандидатов.

Основные контролируемые сравнения: index 1/3/4 — размер fixed; 2/5 — overlap; 1/6 — границы при target 1000; 1/7/8 — embedding. Query 1/9/10 — RRF; 1/11 — глубина пула; 4/12 — число rewrite; 12/13 — модель rewrite. Query 2/5/6 и 3/7/8 дают кривые качества по объёму контекста. Смена answering- и judge-модели здесь не выполняется: обе остаются на существующей настройке Qwen3.5 9B.

**Gold-разметка новых разбиений.**

Чанки всех профилей получены существующими `FixedSizeChunkerService` и `RecursiveChunkerService`, без копирования алгоритма на другой язык и без вызовов Ollama. Для новых layout-профилей 3–6 выделены точные evidence-фрагменты исходных книг, затем найдены пересекающие их новые чанки. Целый фрагмент получает исходную релевантность 2/3, часть фрагмента — максимум 2; чанки дедуплицируются. В `experiment-evidence.json` сохранены цитаты, исходные offsets и SHA-256 книг для проверки происхождения разметки.

У профилей 7/8 разбиение побайтно совпадает с ID 1, поэтому их gold-разметка является точной копией ID 1. Для unanswerable gold остаётся пустым у всех восьми профилей. Эталоны 1/2 не пересматривались: это сохраняет прежний baseline, включая известные ограничения его разметки.

Flat Recall@k по chunkId всё ещё учитывает альтернативные упоминания и части разорванного evidence отдельно. Поэтому вместе с ним нужно анализировать ответы и полученные тексты. Ручная проверка нового evidence и спорных вердиктов судьи остаётся полезной перед окончательными научными выводами.

**Подготовка моделей.**

К уже используемым `qwen3-embedding:8b` и `qwen3.5:9b` нужны три модели:

```powershell
ollama pull qwen3-embedding:0.6b
ollama pull qwen3-embedding:4b
ollama pull qwen3.5:4b
```

Приложение автоматически модели не скачивает. До запуска убедиться, что Ollama доступна по настроенному адресу. Модели в ходе подготовки профилей не запускались.

**Запуск на Windows из корня проекта.**

```powershell
.\gradlew.bat build
Set-Location build\libs
java -jar urag.jar profiles index
java -jar urag.jar profiles query
java -jar urag.jar report dataset
```

Для уже открытого интерактивного приложения, запущенного из `build\libs`:

```text
/report dataset
```

Если JAR запускается из корня проекта, соответствующий путь к датасетам — `examples/dataset`:

```powershell
java -jar build\libs\urag.jar report examples/dataset
```

Рабочая директория определяет расположение `.data` и отчётов. Для продолжения прежнего эксперимента с базой `build\libs\.data` использовать вариант с переходом в `build\libs`. Build штатно копирует обновлённые книги и датасеты в эту папку.

Существующие готовые индексы будут пропущены. Новые index-профили создадут отдельные индексы; прежние JSON не изменены, поэтому их хеши сохраняются. Для корректного сравнения времени полной индексации учитывать статусы INDEXED/SKIPPED отдельно.

После индексации нескольких embedding-моделей ручной dense/hybrid поиск следует ограничивать `--index ID` конкретного сохранённого индекса. Это ID из базы, а не номер index-профиля. Поиск по всем индексам одной книги может смешать несовместимые embedding-модели; `/report` сам выбирает конкретный индекс для каждой оценки.

Полный перебор значительно длиннее предыдущих 240 оценок. Нельзя надёжно оценить его время простым умножением: меняются модели, размер контекста и число новых индексов. После завершения для анализа нужны новая папка `reports/run-...` и связанные `.data/logs`.
